# LCARS

The `LCARS` demo is a practical implementation of the `text2pydough` system, demonstrating how Large Language Models (LLMs) can translate natural language instructions into executable PyDough code. This demo serves as a core evaluation and exploration interface, allowing users to test the capabilities of different AI providers in generating code for structured data queries.

The demo is implemented in Python using Jupyter notebooks and integrates multiple AI backends (e.g., Claude, Gemini, DeepSeek) to produce and evaluate PyDough code over the TPC-H benchmark database. It provides an end-to-end pipeline from user query to data output and explanation.

We recommend starting with the most recent notebook `llm_demo_final_vRK_v2.ipynb`, which illustrates the complete workflow using updated API structures.

> [!IMPORTANT] 
> Before running any notebooks:
> - Ensure that the SQLite database `tpch.db` is located in the root directory.
> - Place the following files in the appropriate location:
>   - `cheatsheet_v6.md`: Reference for PyDough syntax and operators
>   - `tpch_demo_graph.json`: Metadata graph used to map relationships between tables and guide query generation
>   - `demo_queries.json`: Example natural language queries
>   - `prompt.md`: Prompt templates for AI providers
> - Ensure that all required API keys and model configurations are properly set in a `run.sh` script. This file is used to define runtime environment variables and custom paths for launching the notebooks.

## Notebook Workflow

Each notebook follows a standard workflow:

1. **Setup & Basic Usage of the API** 
   First, the notebook imports the LLM client:

   ```python
   from llm import LLMClient
   client = LLMClient()

2. **Query Execution**  
   The user inputs a natural language query:

   ```python
   result = client.ask("Show the top 5 customers by total revenue")
   ```
3. **LLMCient class**

This class is in charge of orchestrating the interaction with the models and their execution. 

It implements the following key methods:

- ask(question, is_corrected=True): Main entry point to generate an answer from a user's question.
- discourse(result, follow_up): Handles follow-up queries with context from previous results.
- get_pydough_code(text): Executes generated PyDough code and returns a DataFrame.
- get_pydough_sql(text): Converts PyDough code to SQL.
- correct(result): Attempts to auto-correct failed code generations.
- add_definition(new_definition): Allows to add an additional definition. The definitions are an additional support to the questions that need them.

4. **Result Analysis**

The `Result` class defines several attributes that are populated during the query process:

- `result.code` → PyDough code generated by the LLM 
- `result.sql` → SQL translation of the PyDough code 
- `result.df` → A DataFrame containing the query results 
- `result.full_explanation` → Full natural language explanation from the LLM 
- `result.exception` → Error trace if the execution fails 
- `result.original_question` → Original natural language question from the user 
- `result.base_prompt` → Full prompt sent to the LLM 
- `result.cheat_sheet` → Reference sheet used in the prompt 
- `result.knowledge_graph` → TPCH metadata graph included as context 

5. **How Attributes Are Populated**

Within the `ask()` method of the `LLMClient`, the attributes are assigned as follows:

- `result.code` is extracted using regex from the LLM’s response 
- `result.full_explanation` contains the full unparsed LLM output 
- `result.base_prompt`, `result.cheat_sheet`, and `result.knowledge_graph` are loaded from system files 
- `result.sql` is produced by calling `get_pydough_sql()` on the extracted code 
- `result.df` is obtained by executing `get_pydough_code()` against the TPCH database 

6. **Example Usage in Notebook**

The demo notebook documents how to access and explore each of these attributes, providing a detailed breakdown of query results and model behavior.

> **Note** 
> All these attributes are available after calling `client.ask()`. Some values (like `df` or `sql`) may be `None` if the execution fails. The `exception` field is only set when an error occurs during PyDough code execution.
